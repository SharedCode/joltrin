    How it works

    The agent and the verifier are separate.

    An agent that proposes an action and also judges it safe can be wrong in both places for the same reason. Joltrin keeps the two apart. The agent emits intent. The check runs outside the agent's context window, against the steps the server has actually recorded and the runbook's rules. The check is Go code, so it gives the same answer for the same trace and rules, and the system that performs the action decides whether to wait for it.

    Order matters most where an action is hard to undo: dropping a database, changing infrastructure or network topology, moving money, rotating credentials. In those cases the wrong order is the failure, and a runbook can state the right order once and check it on every call. The flow is: the agent proposes a step, Joltrin checks it against the recorded trace and the rules, a missing prerequisite comes back as a structured block, the agent runs the steps it names or stops and asks, and the integrating system lets the action through only after the check passes.

    // How the verification barrier sits between the agent and real systems
    1. AI Agent
    Emits intent: a tool call, API mutation or shell command
    2. Verification Barrier
    Checks preconditions and safety rules against the run's trace
    3. Decision
    ALLOW (step committed) BLOCK (nothing runs, fix returned)
    4. Real Target
    Databases, Cloud APIs, K8s, MCP / A2A Services
    Preconditions

    A step is blocked until the states it needs have been established in the run's trace. What the agent claims does not count. A backup must be validated before a drop.

    Safety rules

    A rule can forbid reaching a state unless another state already holds, for example no database drop without a validated backup.

    Rollback stays reachable

    When a runbook is registered, it is checked that rollback can still be reached from every state. A runbook that can dead-end is refused.

    Or drive it from LangGraph

    A StateGraph with an agent node, a ToolNode over the server's MCP tools, and a loop between them. The agent tries drop_prod_db, reads the block, runs the steps it names, and retries. With ANTHROPIC_API_KEY set, a Claude model makes the calls. Without it, a small scripted policy stands in so the example runs offline and in CI. The policy is not a language model.

    That output is from a run of examples/langgraph_agent/agent.py with the scripted policy. Source and setup.

    A block tells the agent what to do next.

    A blocked call is a normal result, not an exception or an opaque error. It says what is missing and which recorded step would establish it, so the agent can replan instead of retrying the same call. 

    {
  "blocked_by": "precondition",
  "missing_state": "backup_validated",
  "established_by_steps": ["validate_backup"],
  "attempts": 1,
  "next": "run_established_by_steps"
}

    blocked_by names the rule that stopped the step. missing_state is what has not been established in this run. established_by_steps lists the steps that would establish it.

    Read it as a replan signal. attempts counts how often the same step was blocked for the same reason in this run, and next says whether to run those steps or stop and ask. Retrying the same call with different parameters will not change the answer.

    With memory turned on, the server also counts, per rule, how many runs it blocked and how many of those went on to commit the step. That shows whether a rule is catching bad plans or is set too strict. It is a count, not an analytics product.

    Agents hand off work. The barrier checks every call.

    Jira, Grafana, AWS, and PagerDuty agents hand off work. Every call passes three checks first: the tool is on that agent's allowlist, any claim matches evidence a tool returned, and the steps it depends on have committed.

    Questions teams ask before trying it
    
      
    
        
    
          What do I have to build?
          
    You name the risky tool and the steps that must come first, then route the agent's call to that tool through Joltrin. It runs in your own environment as a Go library or as an MCP or A2A server. If the agent can reach the tool another way, Joltrin cannot stop that call.
    
        
    
        
    
          Can't the agent just say the backup is done?
          
    If the agent records its own steps, yes. Joltrin checks the recorded steps, not the real world. Steps that matter should be recorded by a tool you trust, such as the result of a backup check, and not by the agent's word.
    
        
    
        
    
          How is this different from permissions or approval prompts?
          
    Permissions decide who may call a tool. Approvals ask a person every time. Joltrin decides whether the earlier steps happened, so safe orders go through on their own and risky ones wait. Use them together.

    Real
    
          
    The checks. The same verify package serves the MCP and A2A servers and compiles to WebAssembly for the live demo, and the repository has tests for it. A recorded run with real agents covers one runbook over MCP.
    
        
    
        
    
          
    Simulated

    Not covered
    
          
    The barrier only answers, so whatever performs the real action must wait for it. It cannot see what the trace does not contain: a backup in another cloud account has to be represented by a step you trust, such as one that checks that account and then records the result. A committed step in the trace means the barrier allowed it, not that the action happened in the world. It does not judge whether an agent's own claim is true, and it does not replace sign-in, access control or isolation around the systems that act.

          Supporting capability
        
    
        
    
          Durable state underneath.
        
    
        
    
          When an agent's process restarts, a network connection drops, or a container gets evicted, whatever it was holding in memory is gone. Joltrin gives it durable state, transactional checkpoints, and a deterministic way to recover.
        
    
      
    

      
      
    
        
    
          
    1. Durable State
    
          
    Survives restarts
    
          
    
            State is written to local copy-on-write B-trees or to clustered storage, not to a cache that disappears with the process.
          
    
        
    

        
    
          
    2. Checkpoints
    
          
    Atomic checkpoints
    
          
    
            Record each step atomically. If an agent fails on step 8 of 10, it resumes from the last committed step, not from the start.
          
    
        
    

        
    
          
    3. Recovery & Rollback
    
          
    Rollback on failure
    
          
    
            A transaction that fails before it commits is rolled back, so a half-finished change is not left behind. Commits use two-phase commit.
          
    
        
    

        
    
          
    4. Vector Similarity
    
          
    Vector search
    
          
    
            Recall similar past episodes and facts by cosine distance. The index lives in the storage engine.
          
    
        
    

        
    
          
    5. Persistent Working Context
    
          
    No network hop
    
          
    
            Runs inside your application binary, or in the browser on OPFS (Origin Private File System), so reads do not cross a network.
