What I built in Joltrin

I have written about 445 commits in this repository, and not only the pipeline around the code. These are the parts that agents and clusters actually talk to:

  • MCP server. sop-mcp-server exposes the verification engine to agents over the Model Context Protocol. It installs with one line, ships as small prebuilt binaries on every release, and registers itself by full path so a missing PATH entry cannot break it. Blocked and malformed requests get structured, actionable errors.
  • A2A agent and bridge. An Agent2Agent endpoint over the same engine, its agent card, and an MCP-to-A2A bridge with tests and setup docs.
  • Kubernetes admission gate. sop-k8s-gate is a validating admission webhook written with the standard library only, so the core module gained no dependencies. The API server refuses a delete until the steps before it are recorded for that trace. It reloads its certificate on rotation and ships with cert-manager manifests, Prometheus counters, an audit log, a deny-egress network policy, a signed and scanned image build, a Kyverno image check in the AKS demo, and a script that reproduces the checks on a real kind cluster.
  • Clients and examples. A LangGraph agent over MCP that recovers from a block, with its own CI run, and a Rust client for the gate command.
  • Delivery. The race, coverage and staticcheck gates, release pipeline, site deploy and rollback that ship all of the above.

The commit history is public in the repository, so you can check each of these. Gerardo wrote most of the core storage code these sit on.

How that shapes Joltrin

  • Stop the risky step, then say what comes first.

    A release pipeline does not just fail a bad deploy. It tells you which check to run. Joltrin works the same way: it blocks a risky agent step, like dropping a database, until the steps before it are recorded, and tells the agent what to do first.

  • Let people try it before they trust it.

    You can run the barrier in your browser, and the core is open source under the MIT license, so you can read exactly what it does.

  • Keep the workflow readable.

    The automation I have seen last is the kind a new engineer can follow in an afternoon. I try to keep Joltrin's rules and checks that plain.

Background

Gerardo is a software engineer based in Union City, California. He made the first commit of this project in April 2015, when the repository was named SOP, for Scalable Objects Persistence, and he has written most of the code since. As of November 2026 that is more than 1,900 of the repository's roughly 2,400 commits.

The project began as a Go library for storing objects durably, built around a transactional B-tree. It is now durable memory and a verification barrier for AI agents in one embedded Go library, and the B-tree is still at its core. You can try the B-tree yourself in the B-tree game.

Gerardo also publishes TensorTree, a vector database in Go built on the same B-tree.
